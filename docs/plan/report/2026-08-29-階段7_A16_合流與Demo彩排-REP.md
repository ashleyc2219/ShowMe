## 實作邏輯

A16 是**唯一一篇不寫程式的計劃**。它要做的是「把 A 這一半（`showme/`）跟 B 那一半
（`overlay/overlay.js`）第一次真的接在一起跑一遍，確認接縫沒歪」。所以本階段
`showme/**`、`tests/**`、`overlay/**` **一行都沒改**，所有驗證腳本都寫在 scratchpad，不進 repo。

A16 的工作天然分成兩類：

```text
┌─ 機器能驗的（本次全做完）────────────────────────────────────────────┐
│ Step 1-1  pytest -m browser                                          │
│ Step 1-2  接縫 14 項  ← PlaywrightBrowser + 真 overlay 打真示範站     │
│ Step 1-3  CSP 紅字檢查（page.on("console")）                          │
│ Step 2/3  示範站 :3000、dev_open.py headed Chrome                     │
│ Step 5    程式化彩排  ← ShowMeApp() 預設 factory，走產品那條路         │
│ Step 6    checklist 中「環境」「Overlay」兩段                          │
└──────────────────────────────────────────────────────────────────────┘
┌─ 需要 Qoder IDE 或真人的（標「待使用者」，沒有打勾）──────────────────┐
│ Step 4    在 Qoder 對話框打那句話、看 agent 自己排步驟                 │
│ Step 6    Qoder 段（MCP 設定、allow list、Request Timeout）／現場／備案 │
│ Step 5    六個空格裡的 Request Timeout 與 demo 用的 timeout_s          │
└──────────────────────────────────────────────────────────────────────┘
```

「程式化彩排」的意思是：**不經過 Qoder，但走 Qoder 會走的完全同一條路**——
用 `ShowMeApp()` 的**預設** `browser_factory`（`PlaywrightBrowser()` → `headless=False`
→ `channel="chrome"` 的本機 Google Chrome + 預設 `overlay_path` = B 的真 overlay），
依序呼叫四個 tool。差別只在「人」被腳本的 `page.click` / `page.fill` 取代：

```text
       真正的 demo                      本次的程式化彩排
   ┌──────────────┐                 ┌──────────────────┐
   │ Qoder Agent  │                 │ scratchpad 腳本   │  ← 只呼叫四個 tool
   └──────┬───────┘                 └────────┬─────────┘
          │ MCP stdio                        │ 直接 await app.<tool>()
   ┌──────▼───────┐                 ┌────────▼─────────┐
   │ ShowMeApp    │  ← 完全一樣 →   │ ShowMeApp()      │  預設 factory
   └──────┬───────┘                 └────────┬─────────┘
          │ Playwright                       │ Playwright
   ┌──────▼───────┐                 ┌────────▼─────────┐
   │ headed Chrome│  ← 完全一樣 →   │ headed Chrome    │
   │ + 真 overlay │                 │ + 真 overlay     │
   └──────┬───────┘                 └────────┬─────────┘
          │                                  │
       真人點                          page.click（扮演人）
```

## 遇到的問題與怎麼解決

### 1（腳本 bug，自己的）`AttributeError: 'dict' object has no attribute 'startswith'`

第 5 項驗 `snapshot(2)` 的 uid 時，我把 `raw2["elements"]`（一串 dict）當成一串 uid 字串在迭代。
改成 `e["uid"].startswith("s2-")` 就好。**跟 overlay 無關。**

### 2（真發現）finefoods-antd 整站沒有 `role == "textbox"`

彩排第 3 步要找一個 textbox 做 `kind="input"`，結果 `[e for e in page["elements"] if e["role"] == "textbox"]`
是**空的**。用探針掃 DOM 才知道原因：

```text
header 的搜尋框：<input type="search" role="combobox" placeholder="Search by Store ID, ...">
                                      ^^^^^^^^^^^^^^^  antd 的 AutoComplete 自己掛上去的
```

overlay 的 `roleOf()` 是**顯性 `role` 優先**（ARIA 精神，作者指定的 role 贏過原生標籤語意），
所以它被歸成 `combobox` 而不是 `textbox`。

**這不是 bug，也不是接縫錯**：`kind="input"` 的完成判定看的是元素本身的 `blur`／`change` 事件
加上 `value` 非空，跟 role 標籤完全無關。解法是挑 uid 時放寬條件——改用
「`role == "combobox"` 且 `name` 含 `Search`」，並先 `evaluate` 確認 `tagName === "INPUT"`。
換了之後 `page.fill` + `blur()` 立刻回 `step_done`（`elapsed_s=0.0`）。

**demo 的影響**：要示範 `kind="input"` 時，agent 不能只找 `role == "textbox"`。已寫進 A16 §7 1-2 的實測發現。

### 3（真發現）`start_tutorial` 剛回來時 `page.elements` 可能是 **0 筆**

彩排第一步 `start_tutorial("http://localhost:3000", ...)` 回來時 `元素數 = 0`。
原因是 finefoods-antd 是 SPA，`page.goto` 的 `load` 事件比 React 把側邊欄 render 出來還早，
snapshot 拍到的是空殼。等 2 秒再 `inspect_page` 就變成 44–67 筆。

**不是 bug**，A16 §9 排錯表本來就有這一列（「回傳的 page 幾乎沒有元素 → 頁面還在載入」）。
腳本裡的處理就是照它寫的：元素太少就 `await asyncio.sleep(2)` 後 `inspect_page` 重拍。
**demo 的影響**：agent 的第一個動作最好是 `inspect_page` 再挑 uid，或 demo 前先把示範站點過一輪 warm 起來。

**主控在彩排後的處理**：這是現場會咬人的 timing 問題，改成靠 agent 記得先 `inspect_page` 太脆弱，
所以在 `showme/app.py::_take_snapshot` 加了最小重拍：拍到空清單就 `sleep(0.5)` 再拍，最多 `SNAPSHOT_RETRIES=3` 次，
重拍沿用同一個 snapshot#（規格是「每產生一次 snapshot 才 +1」）。TDD：`tests/test_tool_start.py` 新增兩條
（第一拍空、第二拍有 → 回 `s1-*` 且 `snapshot_no == 1`；整頁真的沒元素 → 拍滿 3 次回空清單、不卡住）。
之後全套 `uv run pytest -q` 171 passed。

### 4（環境差異）第 7 項在 finefoods 上踩不到 150 上限

A16 原文說「finefoods-antd 的列表頁元素多，看 `count` 是不是 150」。實際掃過四個頁面，
最多的首頁也只有 67 個白名單元素，`truncated` 一律 `false`——**上限根本沒被觸發，等於沒驗到**。

解法：另寫一支腳本，在頁面上**臨時**注入 200 顆 `<button>` 再 `snapshot`，
拿到 `count=150`、`truncated=True`、最後一筆 uid `s2-150`，驗完把 probe 節點 `remove()`。
沒有動 `sample-app/` 任何檔案。

### 5（沒發生的問題）CSP

A16 §7 1-3 花了整節講 Driver.js 被 CSP 擋的症狀。**實測完全沒有發生。**
原因是 B 已經走了設計 §12 的「本地 vendor 檔」那條路：`overlay/overlay.js` 是
`overlay/build.sh` 把 `overlay.src.js` + `vendor/driver.iife.js` + `vendor/driver.css`
（內嵌成 `__SHOWME_DRIVER_CSS__` 字串）串成的單一 517 行 bundle，執行期不去 CDN 拉任何東西。
所以整段症狀不會出現，**不需要告知 B**。
